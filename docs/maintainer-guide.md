# 维护人编写指南

先阅读 [设备仓库编写规范](repository-standard.md)，再按以下顺序完成自己的设备仓库。

## 1. 确认设备和职责

确认准确型号、负责人的 GitHub 用户名、设备位置、适用设备编号及现有控制方案。型号相同但配置不同时，先确定第一版说明覆盖哪台设备。

UR5 第一版只覆盖其中一台时，应明确写出设备编号；不要直接声称流程适用于两台。

## 2. 复制通用模板

参照 [模板使用说明](../templates/README.md)，将 `device-repository` 目录中的内容复制到自己的设备仓库根目录，然后填写占位字段。不要把整个 Hub 仓库或设备仓库的 `.git` 目录相互复制。

通用模板只在 Hub 中维护。Panda 是实际填写的示范，设备专用参数不能未经确认照搬到其他设备。

## 3. 先跑通一条使用路径

先记录真实软硬件环境，再编写并验证一个最基础的 Demo。以这个 Demo 为终点，补齐快速上手中的硬件连接、开机、连接检查及结束步骤。

这一步优先做到可复现。更多 Demo、照片和扩展功能可后续补充，并保留明确的内容状态。

## 4. 整理资料和问题

在 `docs/README.md` 汇总匹配的官方资料；在 `lab-configuration.md` 写实验室实际配置；在 `troubleshooting.md` 记录遇到的问题、定位过程及解决方法。

出现的新问题经解决后，补入对应设备仓库，方便下一位使用者查询。

## 5. 找新人试用

请一位具备 Linux、Python、ROS 基础、但未用过这台设备的同学，在满足必要培训或现场指导条件后按文档完成首次操作。

记录卡住的位置和需要额外口头说明的内容，修订后再填写验证记录。只写好文档而没有实际运行时，状态仍为“待验证”。

## 6. 接入总导航

向 Hub 维护人提供设备准确名称、数量、负责人、位置、设备照片和仓库地址。设备存在多种配置时，说明当前文档覆盖范围。

总导航只更新介绍和入口；完整运行步骤留在设备仓库。

## 7. 提交前检查

- 三大入口和图片的相对链接能打开。
- 占位字段已按实际情况填写，剩余未知项有明确状态。
- 命令的目录、参数、环境依赖和停止方法明确。
- 已验证内容附验证人、日期及代码版本。
- 公开前检查图片、配置和附件是否适合对外提供。

提交与推送按各仓库负责人的约定执行；本指南不要求自动提交或自动推送。
