# 设备仓库编写规范

本规范适用于 FSII Robotics LAB 的机器人及相关实验设备仓库。读者默认已掌握 Linux、Python、ROS 基础；教程从实验室实际设备的硬件连接和程序启动开始。

## 1. 仓库之间的关系

- `FSII-Robotics-Hub`：设备介绍、负责人、统一导航、编写规范和通用模板。
- 设备仓库：该设备的操作说明、技术资料索引、配置与 Demo。
- 同型号且流程相近的多台设备优先共用一个仓库。UR5 两台共用仓库，先写明其中一台的流程，再记录另一台的差异。
- 科研项目中专用的实验代码可放在项目仓库；设备仓库保留通用示例及必要的项目入口。

这些是组织下相互独立的 Git 仓库，通过普通链接关联，无需 Git 子模块。

## 2. 基本目录

```text
device-repository/
├── README.md
├── quickstart/
│   └── README.md
├── docs/
│   ├── README.md
│   ├── lab-configuration.md
│   └── troubleshooting.md
├── demos/
│   ├── README.md
│   └── example_demo/
│       └── README.md
├── configs/                 # 按实际需要保留
└── assets/                  # 按实际需要保留
```

`README.md` 和三大入口 `quickstart/`、`docs/`、`demos/` 应保持一致。Demo 的代码可以按实际 SDK、ROS 包或其他项目结构组织，不要求为统一目录移动原有工程。

通用骨架位于 [device-repository](../templates/device-repository/README.md)。其中的 `example_demo` 是文档模板，不是可运行程序。

## 3. 首页要求

设备仓库首页至少包含：

- 准确的设备名称和型号、照片（具备后补充）、设备用途。
- 维护负责人及联系入口、设备所在位置。
- 文档适用的具体设备；多台设备时使用明确编号，不以“左边那台”等临时描述替代。
- 三大内容入口，以及当前内容建设与验证状态。
- 返回 [总导航](https://github.com/FSII-Robotics-LAB/FSII-Robotics-Hub) 的链接。

设备名称使用正式拼写，已确定的 Panda 仓库名称为 `Franka_Panda`。其他仓库命名由负责人确认后登记到总导航，不提前生成不存在的远程链接。仓库名称与内部 ROS 包名不必一致。

## 4. 快速上手要求

快速上手是一条从硬件准备到正常结束的连续流程，至少说明：

1. 适用设备与环境：设备编号、系统、ROS 或控制框架、SDK 及固件等实际版本。
2. 操作前准备：所需线缆、控制电脑、供电、末端工具、必要培训或现场指导条件。
3. 硬件连接与开机：连接示意、连接顺序、设备就绪的判断方式。
4. 连接检查与程序启动：实际命令、执行位置、配置文件及需要替换的参数。
5. 首次操作：引用一个已验证的基础 Demo，说明正常输出或设备现象。
6. 停止与关机：正常停止顺序、设备急停位置及异常时的处理入口。

不重复教授 Linux、Python、ROS 基础。存在额外依赖时说明前置条件并链接对应资料。

快速上手直接引用基础 Demo 的详细运行方法，避免在两处维护相同命令。关键连接与结束步骤仍保留在快速上手中。

## 5. 官方资料与实验室文档

`docs/README.md` 是资料索引，区分以下内容：

| 类型 | 需要说明的内容 |
| --- | --- |
| 官方手册、SDK/API、厂商示例 | 标题、官方来源链接、适用型号和版本、用途 |
| 实验室配置 | 实际软硬件版本、连接方式、控制器和末端工具配置、多台设备的差异 |
| 标定、扩展与故障处理 | 实际步骤、适用条件、已知限制及验证状态 |

官方资料优先提供来源链接。确需保存附件时，确认允许分享，并注明来源、版本及适用设备。大体积录像、数据和系统镜像使用组内存储链接，同时说明访问方式。

## 6. Demo 要求

`demos/README.md` 列出示例功能、仿真或真机要求、适用设备、验证状态和入口，并推荐一个首次上手示例。

每个 Demo 独立说明：

- 功能与运行方式：仿真、真机或其他设备配合。
- 实际依赖版本及设备初始条件。
- 代码或官方示例的准确位置、必要配置和启动命令。
- 预期输出或设备行为，以及如何判断成功。
- 可调整参数、正常停止方法和常见问题。
- 验证人、验证日期及对应代码版本或提交编号。

直接使用官方示例时，注明来源及版本，并写清实验室的实际运行方式，无需重复复制整套厂商代码。

## 7. 真实性与验证状态

统一使用以下状态，避免把目录完整误认为教程已经可用：

| 状态 | 含义 |
| --- | --- |
| 待填写 | 具体内容尚未提供 |
| 待验证 | 已写出步骤，但尚未在对应环境完成验证 |
| 已验证 | 已在注明的设备、环境和代码版本上完成操作，附验证人与日期 |

禁止把推测的 IP、版本、启动命令或功能写成实验室的已知事实。缺少的信息明确标注；未验证的步骤不能标为已验证。

设备连接参数应区分公开示例和实际配置。密码、令牌、私钥等不进入仓库；可提交不含凭据的配置示例，并说明如何在本地填写。

## 8. 维护方式

主维护人负责内容准确性、问题整理和交接；有备份维护人时也在首页登记。使用者可通过 Issue 反馈，通过 Pull Request 补充说明。

涉及环境、配置或运行流程的更新，同步更新相关文档和验证记录。交接时由接手人按文档运行一次基础流程，将额外需要口头解释的内容补入文档。

## 9. 第一版完成条件

- 首页设备身份、负责人和三大入口明确。
- 一条完整且已验证的快速上手路径。
- 一份能找到对应型号和版本的资料索引。
- 至少一个已验证的基础 Demo，有明确的预期结果和结束方法。
- 所有未知项及未验证内容均有标注，文档链接有效。

目录骨架可以先建好，但不能据此宣称设备仓库第一版已经完成。
